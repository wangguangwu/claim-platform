# Spec 编写规范

本文件负责 `docs/specs/<feature-name>/` 的建与不建、三个文件各自写什么、三者如何保持一致。项目长期公共约束的归属见 `docs/specs/baseline.md`，什么时候建 Spec 在执行流程中的位置见 `docs/engineering/workflow.md`。

## 1. 何时需要 Spec

Feature 级改动需要建立 Spec：

- 新增或改变业务能力、业务规则、状态流转；
- 新增或变更跨上下文 API、领域事件、共享契约；
- 改变领域模型、数据库边界、租户模型或前端功能域划分；
- 需要多人/多步协作、跨多个模块的关键缺陷修复。

轻量改动不需要 Spec，直接按 `docs/engineering/workflow.md` 开发与验证：

- 不改变业务行为的缺陷修复、补测试、日志与告警补充；
- 局部重构、命名与包结构调整；
- 配置、文档、文案改动。

轻量改动仍然受 `docs/specs/baseline.md` 约束；做起来发现已经越界到上面的 Feature 级情形，就补建 Spec 再继续。

## 2. 目录与文件

```text
docs/specs/<feature-name>/   # 小写 kebab-case，一个功能一个目录
├── requirements.md          # 要解决什么
├── design.md                # 打算怎么实现
└── tasks.md                 # 拆成可执行任务
```

- 三个文件固定存在，不新增其他文件，不做 `FR-xxx → DS-xxx → TK-xxx` 编号回链和追踪矩阵。
- 一个 Feature 的 Spec 尽量短：能一句话说清的规则不要展开成段落，不复述代码里已经能看到的东西。
- `docs/specs/baseline.md` 已经定义的公共需求与约束，Feature 文档不重复，只写本 Feature 的增量；与基线冲突时按 `docs/specs/baseline.md`「与功能 Spec 的关系」处理。

## 3. requirements.md

只描述问题与目标：

- 背景与要解决的问题；
- 目标与非目标；
- 需求与业务规则（状态流转、失败行为、幂等语义、租户影响）；
- 所属限界上下文与范围 / 非范围；
- 验收标准（用什么行为判定做完了）。

禁止出现：实现任务、类与接口设计、表结构、技术选型、开发排期。写了实现就已经越界到 `design.md`。

## 4. design.md

描述具体实现方案：

- 核心链路（入口 → 应用用例 → 领域行为 → 持久化 / 消息 / 外部调用）；
- 数据模型：聚合、状态与不变量、表与字段归属、迁移方式；
- 接口与契约：API、命令、查询、领域事件、错误码及其触发条件与兼容性影响；
- 组件与包位置：新增或修改的类落在哪个模块哪一层；
- 异常处理：失败分类、重试 / 死信 / 补偿、并发与幂等实现；
- 测试策略：需要覆盖的场景与验证方式。

可以出现具体技术和类设计，但不写任务清单；任务清单属于 `tasks.md`。

## 5. tasks.md

根据 `design.md` 拆出的可执行 Checklist：

```markdown
- [ ] 任务：一句话说明改什么、在哪一层
```

- 每个任务必须能明确判断完成或未完成，粒度以一次连续开发可交付为准。
- 只写动作和位置，不重复 `design.md` 的正文；验证证据、耗时、逐任务评审记录不进任务清单。
- 勾选只在该任务通过 `docs/engineering/workflow.md` 第 6 节适用验证后进行。

## 6. 一致性规则

`requirements.md → design.md → tasks.md` 必须保持一致：每项需求有设计承接，每项设计有对应任务，任务不引入需求之外的功能。

开发过程中发现需要调整时，按顺序改文档，再继续写代码：

| 变化 | 同步顺序 |
| --- | --- |
| 需求或业务规则变化 | 先改 `requirements.md`，再改 `design.md`，最后同步 `tasks.md` |
| 设计方案变化 | 先改 `design.md`，受影响时同步 `tasks.md` |
| 只有进度或实现细节变化 | 只更新 `tasks.md` |

禁止只改代码不回写文档；不得用未记录的实现决策绕过 Spec。

## 7. 交付与清理

- 功能交付后直接删除 `docs/specs/<feature-name>/`，不保留归档目录。
- 删除前必须把 Spec 中长期有效的结论回写 `docs/specs/baseline.md` 的对应章节：已确定的命名、保留契约、既定业务规则。只服务于本次实现过程的临时内容（改动映射表、实施顺序、验证记录）不回写。
- 结论未回写干净不得删除 Spec。
- `docs/specs/` 只保留 `baseline.md` 和未完成的活动 Feature 目录，目录说明由本文件承担。
