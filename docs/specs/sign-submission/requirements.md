# 签收提交需求

## 项目背景与目标

仓库已有 Claim Platform 的长期架构基线，但尚未有可运行服务。`sign-submission` 作为首个交付能力，建立租户将一笔理赔申请提交为平台 `Sign` 的最小闭环，并为后续材料处理链路留下可异步推进的业务事实。

## 目标与非目标

### 目标

- 受信任租户上下文中的调用方能够提交一笔平台标准签收申请，并得到可查询的 `signNo`。
- 同一租户对同一 `externalApplyNo` 的重复提交具备可预期的幂等语义：回放已创建的结果，或在并发窗口返回可重试冲突。
- 成功签收同时保存签收事实、随申请提交的材料元信息、初始材料处理任务与提交交互审计；任一事实创建失败时不产生半成品签收。
- 签收从 `SIGNED / MATERIAL` 初始状态进入后续材料处理链路；本功能只保证任务可被后续异步能力接管。

### 非目标

- 不处理材料内容上传或材料识别，不执行承保查询、审核同步、问题件、撤销、案件绑定或案件推送。
- 不实现租户 JSON/XML 协议差异、认证验签和加解密规则；本功能只接收网关转换后的平台标准报文，并再次校验调用方租户范围。
- 不定义人员明细；除可检索的 `applicantName` 外，其他申请人相关内容按基线要求进入 `extJson`，且不进入日志或响应。

## 核心业务规则

- 租户身份只取自受信任的 `TenantContext`，忽略请求中试图指定的 `tenantCode`。
- 签收幂等键为 `tenantCode + externalApplyNo`；数据库唯一约束是最终兜底，冲突后必须回查并发赢家并回放结果。回查不到时按编号碰撞或并发异常处理，不能返回未知错误。
- 初始 `Sign` 状态为 `SIGNED`，初始阶段为 `MATERIAL`；初始 `SignTask` 仅表示 `MATERIAL_PROCESS` 的异步意图，不在提交请求内执行外部调用。
- 签收、材料元信息、初始任务和 `SIGN_SUBMIT` 交互日志必须同一事务提交或回滚。`signNo` 发放不位于该事务；允许因事务回滚出现编号空洞，但不允许重复使用。
- 提交交互日志只记录规定的摘要、结果和关联标识，不记录申请明细、材料原文、令牌或外部凭证。

## 所属上下文与范围

- 所属限界上下文：Sign；实现模块为 `claim-sign-service`，由 `claim-gateway` 负责标准报文路由与租户上下文透传。
- 依赖边界：签收服务拥有自己的事实库；不得读取或写入案件推送、承保、审核或内部案件系统的数据。
- 对外 HTTP 根路径、响应信封和既有错误码必须遵循基线。提交方法、请求/响应字段与字段必填规则属于本 Feature 新增契约，必须经用户确认并回写基线后才能编码。

## 验收标准

- 合法的平台标准报文在可信租户上下文下创建一笔 `Sign`，返回稳定的 `signNo`，且初始状态与阶段正确。
- 同一租户的重复提交不创建第二笔签收、材料、任务或提交日志；不同租户可使用相同 `externalApplyNo`。
- 并发提交命中唯一键竞争时，能够回放成功赢家或返回基线定义的可重试签收并发错误。
- 事务中任一事实写入失败时，不存在可见的部分签收数据。
- 未通过租户范围校验、参数校验失败、编号不可用及未预期异常均使用基线规定的 HTTP 状态和 `ApiResult` 响应语义，且响应与日志不泄露敏感信息。
