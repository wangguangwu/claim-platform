## 背景

`main` 上的签收服务已有主代码 129 文件 / 5456 行、测试 46 文件 / 5245 行，而蓝本 §5.1 的签收主链路只要求 `SignRequest → SignCommand → Sign → SignRepository`。体量集中在两处蓝本没有要求、或与 §4 归属冲突的实现：租户协议适配整簇（本应位于网关）、人员信息强类型四件套（蓝本 `Sign` 聚合不含人员对象）。

本轮做减法：把与蓝本不符且不承载业务价值的实现删除，保留已验证正确的机制，不新增任何能力。

## 目标

- 租户报文解析、协议路由与转换从签收服务删除，签收服务只接受平台标准模型。
- 人员信息不再做强类型建模，退化为原始 JSON 透传。
- 签收主链路行为、发号机制与三级幂等保持不变。
- 输出可复核的删除清单与契约影响，并回写基线的保留契约与已知偏差。

## 非目标

- 不实现问题件（`ClaimIssue`）、撤销（`sign.withdraw`）、材料状态与材料补充。
- 不实现网关侧租户适配、验签与加解密，不实现案件推送服务与前端功能域。
- 不改数据库 Schema、不删表、不删列。
- 不重排全部包结构（上一轮已完成包根迁移，本轮只删除，不做二次挪包）。
- 不改指标名、Redis 键前缀与发号配置。

## 需求与业务规则

1. 签收服务不得再解析租户专有报文；租户差异的归属回到蓝本 §4 的网关（对应基线 §8 偏差表第 1 行）。
2. 幂等键仍为 `tenantCode + externalApplyNo`，三级保障（回放缓存 → 业务锁 → 唯一键）不变。
3. 签收号发号机制（Redis 计数器 + 数据库高水位兜底 + 对账校正 + 启动 Schema 校验）整体保留，配置与键不变。
4. 人员信息只保留 `applicantName` 一个业务字段；申请人、主被保险人、出险人、领款人的强类型对象与转换器删除，其余内容继续通过 `extJson` 原样入库。
5. **对外契约变更（需用户确认后才可实施）**：
   - 删除租户协议端点 `POST /api/v1/tenant-intakes` 及其协议版本路由请求头；
   - `POST /api/v1/claim-intakes` 请求体移除 `applicantInfo`、`accidentPersonInfo`、`mainInsuredInfo`、`payeeInfo` 四个对象字段。
   - 签收详情响应不变：`SignDetailResult` 当前不返回人员对象，本轮也不新增 `extJson` 返回，因此删除人员建模不减少任何已返回字段。
6. `t_claim_intake` 的四列人员 JSON 转为不再写入，登记为数据库待清理项；已有历史行不迁移、不删除。
7. 基线 §8 偏差表中未实现的其余各项（问题件、撤销、材料状态、推送服务、前端功能域、网关能力）本轮不补，改为"暂缓、不排期"，仍保留为偏差登记。
8. 删除即删除：不留兼容壳、不保留空实现、不保留 `@Deprecated` 占位。

## 验收标准

- 签收服务主代码文件数与行数下降到设计清单的量级，且不存在只被删除代码引用的残留类型。
- 全仓编译通过，`mvn verify` 无失败无错误；剩余测试全部真实执行（依赖本地 MySQL 与 Redis 的并发用例不得静默跳过）。
- 签收提交、幂等回放、锁超时与降级、唯一键冲突回查、编号碰撞、租户隔离、材料登记与查询这些既有行为由测试证明未变。
- 代码中不再出现租户协议解析、协议路由注册、人员强类型建模的任何残留。
- 基线 §8 的保留契约表与已知偏差表与实际代码一致，不留下已删除却仍登记为"保留"的条目。

## 确认边界

本 Spec 通过评审仅代表"删除范围与契约影响已确认"。在第 5 条契约变更得到明确确认之前，不删除任何代码——`POST /api/v1/tenant-intakes` 一旦删除即不可由已部署调用方继续使用，回滚需要恢复整套协议适配实现。
