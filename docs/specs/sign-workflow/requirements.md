# 签收流程需求

## 项目背景与目标

平台不能把签收理解为一次“落表接口”。它是理赔前段的流程编排入口：先登记签收事实，再依次推进材料上传与处理、自动承保查询、审核系统同步、内部结果等待；任一业务不满足时进入问题件与补材闭环，恢复后从中断环节继续。

本 Feature 建设 Sign 限界上下文的完整前段流程能力，不建设案件审核、理算、核赔与支付。

## 行业流程对齐

- 受理事实先于后续处理落库，信息不足时仍可作为待补充的受理记录；保单未核验前不能进入后续赔付处理。[Guidewire FNOL 说明](https://docs.guidewire.com/cloud/is/202603/cloudapibf/cloudAPI/ClaimCenter/fnol/executing-fnol/c_the-FNOL-process-in-ClaimCenter.html)
- 资料收集、保险责任核验与审核是理赔前段的常见环节；资料不完整时应一次性通知补充，而不是静默失败。[机动车辆保险理赔管理指引](https://jrj.sh.gov.cn/ztfl-dfjrjg/20220922/f3c98e6fba9f4cc19f31134c0fb4c6f3.html)
- 本平台只承接上述前段交互，不接管案件审核、理算、核赔或保司内部处理；具体材料清单和保险责任规则由租户与外部系统决定。

## 目标与非目标

### 目标

- 创建唯一、可查询、可审计的 `Sign`，以 `tenantCode + externalApplyNo` 防止重复签收。
- 将签收流程按“落表 → 材料上传与处理 → 自动承保查询 → 审核同步 → 等待内部结果”推进；材料、承保、审核均通过可恢复的异步 `SignTask` 执行。
- 支持问题件创建、补充材料、回复和从原中断阶段恢复，不重复执行已经成功的子流程。
- 记录子流程任务的当前状态、最近一次开始/结束时间、耗时、尝试次数与结果摘要，并记录每次跨系统交互的方向、目标、耗时与错误码。
- 不使用数据库物理外键；以业务标识、唯一索引、应用层关联校验和受控状态变更维护一致性。

### 非目标

- 不实现案件审核、理算、核赔、赔付决策；`ClaimCase` 仍由内部案件系统拥有。
- 不定义保司内部材料规则、承保规则或审核规则，只通过租户业务语义 Adapter 与外部系统 Adapter 隔离。
- 不把人员明细结构化建模；除 `applicantName` 外的人员内容进入 `extJson`，且不写入日志或对外响应。

## 主状态机设计

`Sign` 主模型不新增第三个“子状态”字段。用户所称的签收子状态映射为基线既有的 `currentStage`；每个子流程的运行状态映射为该 `SignTask` 的任务状态。

| 签收状态 `signStatus` | 当前阶段 `currentStage` | 业务含义 |
| --- | --- | --- |
| `SIGNED` | `MATERIAL` | 签收已落表，等待材料子流程启动 |
| `PROCESSING` | `MATERIAL` | 正在处理材料上传、校验或归档 |
| `PROCESSING` | `INSURED_QUERY` | 正在自动查询承保信息 |
| `PROCESSING` | `AUDIT_SYNC` | 正在向审核系统同步申请 |
| `PROCESSING` | `WAIT_RESULT` | 审核同步完成，等待审核或内部案件结果 |
| `ISSUE` | 中断时所在阶段 | 因缺件、承保不符或审核驳回等待补件/回复 |
| `COMPLETED` | `COMPLETED` | 已收到内部案件结果并维护 `CaseRelation` |
| `REVOKED` | 撤销前阶段保留作审计 | 已撤销，终态 |

## 核心业务规则

- 租户身份只取自受信任 `TenantContext`，不信任请求中的 `tenantCode`。所有租户业务查询均带 `tenantCode`。
- 提交幂等键固定为 `tenantCode + externalApplyNo`。先查后建，唯一键为最终仲裁；冲突后回查赢家并回放，回查不到时返回可重试并发错误。
- 签收、首批材料元信息、初始 `MATERIAL_PROCESS` 任务和 `SIGN_SUBMIT` 交互日志同一事务提交或回滚；编号申请和外部调用不在该事务内。
- 材料、承保、审核子流程均通过 `SignTask → RocketMQ → Consumer` 执行。Consumer 以 `taskNo` 或业务幂等键处理重复投递，外部调用必须带 `signNo` 或 `taskNo`。
- 技术失败只改变任务执行状态并重试、死信或人工介入，不创建问题件；业务不满足创建 `ClaimIssue`，记录恢复阶段，签收置为 `ISSUE`。
- 回复问题件或提交补件后，系统校验问题件可恢复，再创建 `ISSUE_REPLY_SYNC` 与对应恢复阶段任务；已成功的前置任务不得重复执行。
- 无物理外键不等于无关联约束：写入前必须校验父级业务事实，所有逻辑关联列必须建立查询索引，撤销或终态处理不得依赖级联删除。

## 所属上下文与范围

- 所属限界上下文：Sign；实现模块为 `claim-sign-service`。网关负责协议、安全、路由、限流和上下文透传；签收服务负责业务复核与流程编排。
- 签收服务拥有 `Sign`、`Material`、`SignTask`、`ClaimIssue`、`CaseRelation`、`InteractionLog` 事实；不写案件推送库，不持有 `ClaimCase` 业务字段。
- 新增或明确 HTTP 请求响应、领域事件字段、MQ Topic/Tag 时，须先经用户确认并回写基线后编码。

## 验收标准

- 签收创建后存在完整初始事实、`SIGNED / MATERIAL` 状态、材料处理任务及可审计日志；同租户重复提交只返回同一签收，不产生重复任务或日志。
- 材料、承保、审核任务均能记录开始、结束、耗时、结果和重试；重复消息不重复产生外部业务副作用。
- 材料缺失、承保不符、审核驳回能创建问题件，补件/回复后可从记录的阶段恢复，且不会回退终态。
- 每次外部承保查询、审核同步、问题件通知/回复均有按 `signNo`、`taskNo`、`traceId` 定位的交互日志和 `costMs`。
- 所有表无数据库物理外键；租户隔离、唯一约束与应用层关联校验覆盖正常、异常、并发及恢复场景。
