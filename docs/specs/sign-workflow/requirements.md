# 签收流程需求

签收不是一次"落表接口"。它是理赔前段的流程入口：先落库签收事实并同步返回 `signNo`，再异步完成影像处理、保单判断、自动承保与审核交付；审核打回进入问题件与补材闭环，租户回复后重新提交审核；租户可在流程推进完成前撤销。

本 Feature 建设 Sign 限界上下文的完整前段流程能力，不建设案件审核、理算、核赔与支付。

域内架构基准见 [签收服务架构基准](../../architecture/claim-sign-service.md)，分层、状态机、数据模型与核心时序以其为准；本文件只写业务需求与规则，不复述。

## 行业流程对齐

- 签收事实先于后续处理落库，信息不足时仍可作为待补充的记录；保单未核验前不能进入后续赔付处理。[Guidewire FNOL 说明](https://docs.guidewire.com/cloud/is/202603/cloudapibf/cloudAPI/ClaimCenter/fnol/executing-fnol/c_the-FNOL-process-in-ClaimCenter.html)
- 资料收集、保险责任核验与审核是理赔前段的常见环节；资料不完整时应一次性通知补充，而不是静默失败。[机动车辆保险理赔管理指引](https://jrj.sh.gov.cn/ztfl-dfjrjg/20220922/f3c98e6fba9f4cc19f31134c0fb4c6f3.html)
- 本平台只承接上述前段交互，不接管案件审核、理算、核赔或保司内部处理；具体材料清单和保险责任规则由租户与外部系统决定。

## 目标与非目标

### 目标

- 创建唯一、可查询、可审计的 `Sign`，以 `tenantCode + externalApplyNo` 防止重复签收；同步链路只做唯一性判断、`signNo` 发放、申请与初始材料关系落库、结果返回。
- 异步推进受理链路：影像处理 → 有效保单判断 → 无有效保单时自动承保 → 审核交付 → 等待审核签收结果。
- 支持审核系统多次打回问题件、租户多次回复与补材，回复处理后重新进入等待审核签收。
- 一个签收可关联多个案件；收到审核签收结果后落 `1:N` 案件关系并完成签收。
- 撤销由租户发起并构成强终态；已进入审核阶段的申请还需通知审核系统撤销或作废。
- 事件投递失败与流程中断按当前状态补偿，不引入独立任务模型。
- 不使用数据库物理外键；以业务标识、唯一索引、应用层关联校验和受控状态变更维护一致性。

### 非目标

- 不实现案件审核、理算、核赔、赔付决策；`ClaimCase` 由内部案件系统拥有。
- 不定义保司内部材料规则、承保规则或审核规则，只通过租户适配层与外部系统 Adapter 隔离。
- 不把人员明细建模成领域对象；四类人员信息整体入库，不进入日志与对外响应。
- 不建通用工作流引擎、独立异步任务表或执行事件历史表；不建运营查询服务。

## 状态与业务规则

`Sign` 只有一个状态字段，8 个取值与流转图见架构基准 §2。业务含义：

| 状态 | 业务含义 |
| --- | --- |
| `PENDING_ACCEPT` | 申请已落库，等待异步受理 |
| `ACCEPT_SUCCESS` | 影像处理成功，进入承保判断 |
| `ACCEPT_FAILED` | 影像处理失败，终态并告警 |
| `AUTO_UNDERWRITING` | 无有效保单，自动承保处理中 |
| `WAIT_AUDIT_ACCEPT` | 审核任务已提交，等待审核系统签收 |
| `SIGN_COMPLETED` | 审核签收成功并落案件关系，终态 |
| `ISSUE_CASE` | 审核系统打回，等待租户回复 |
| `CLAIM_REVOKED` | 租户撤销，终态 |

规则：

- 租户身份只取自受信任 `TenantContext`，不信任请求中的 `tenantCode`；所有租户业务查询都带 `tenantCode`。
- 提交幂等采用三层：事实库快查直接回放已存在签收 → `tenantCode + externalApplyNo` 业务锁串行化并发创建 → 数据库唯一键最终兜底。唯一键冲突必须回查并发赢家并回放，回查不到时返回可重试的并发错误。
- 同步创建的事务内只写签收、材料关系、初始状态与提交交互日志；发号与外部调用不在该事务内。
- 只有审核系统的问题件事件可以使签收进入 `ISSUE_CASE`；问题件回复处理完成后回到 `WAIT_AUDIT_ACCEPT`；`SIGN_COMPLETED` 与 `CLAIM_REVOKED` 的申请不得再次进入问题件。
- 影像处理失败置 `ACCEPT_FAILED`，不自动恢复；自动承保未成功保持 `AUTO_UNDERWRITING`，按幂等条件重试或转人工告警。
- 迟到事实（审核结果、问题件、承保结果、补材结果）遇到终态时只记录交互并告警，不推进状态。
- 重复事件必须在校验当前状态后安全结束，不产生重复外部副作用。
- 补偿按当前状态执行明确恢复策略（见架构基准 §4.3），只重发事件或重试幂等外部调用，不直接改写业务状态。
- 每次跨系统交互都留下可按 `signNo`、`traceId` 定位的审计记录。
- 无物理外键不等于无关联约束：写入前必须校验父级业务事实，逻辑关联列必须建查询索引，撤销与终态处理不得依赖级联删除。

## 所属上下文与范围

- 所属限界上下文：Sign；实现模块 `claim-sign-service`。网关只做认证、`tenantCode` 识别、路由与入口限流；租户协议与业务语义差异由签收适配层承载（基线 §5）。
- 签收服务拥有 `Sign`、`Material`、`ClaimIssue`、`CaseRelation`、`InteractionLog` 事实；不写案件推送库，不持有 `ClaimCase` 业务字段。
- 本 Feature 依赖 [平台契约版本化 Spec](../platform-contract-versioning/requirements.md) 完成签收 HTTP 字段、MQ Topic/Tag、问题件业务定位标识与下游错误映射的确认及基线回写；未完成前不得创建 Controller、DTO 与消息定义。

## 验收标准

- 同租户重复提交（含并发）只返回同一 `signNo` 与同一状态，不产生重复签收、材料关系或交互日志；唯一键冲突路径能回放并发赢家的结果。
- 同步签收响应内不含影像、承保、审核调用；事件在事务提交后发布，发布失败由补偿兜底。
- 异步链路按状态推进至 `WAIT_AUDIT_ACCEPT`；无有效保单时走自动承保且以 `signNo` 幂等，重复调用不产生重复承保副作用。
- 审核签收结果携带多个案件号时落多条 `CaseRelation` 并置 `SIGN_COMPLETED`；重复消息不再推进。
- 问题件可多次打回与回复；已 `SIGN_COMPLETED` 或已 `CLAIM_REVOKED` 的申请收到问题件或审核结果时只告警。
- 撤销后所有业务通道都不再推进状态，已进入审核阶段的申请发出撤销通知；通知失败由补偿补发。
- 流程停在可推进状态超过阈值时，补偿按恢复策略重发对应事件，且不重复提交审核任务。
- 所有表无数据库物理外键；租户隔离、唯一约束与应用层关联校验覆盖正常、异常、并发及恢复场景。
