# 平台契约版本化需求

## 项目背景与目标

签收与案件推送的领域边界已确定，但 HTTP 字段、消息路由、问题件定位和外部系统错误映射尚未确认。若在各 Feature 内临时决定，会造成调用方无法兼容、消息无法路由和多次问题件无法正确关联。

## 目标与非目标

- 确认并登记签收资源及其材料、问题件、撤销子资源的请求响应字段、鉴权前提和错误码触发条件。
- 确认 `SIGN_ACCEPT`、`ISSUE_REPLY`、`CLAIM_REVOKE` 与案件生成事件的 Topic、Tag、消费者组、版本和幂等字段。
- 确认多次问题件场景中回复与补充材料绑定具体 `ClaimIssue` 的稳定业务定位标识，以及审核、承保、案件和保司交互的幂等键、错误映射。
- 将确认后的长期结论回写至项目基线或对应服务架构基准，再由业务 Feature 实现。
- 不实现 Controller、DTO、消息收发、外部客户端或 Adapter；不改变现有固定路径、错误码、事件名称和公共事件字段，除非用户明确确认。

## 所属上下文与范围

- 所属上下文：Sign、Push 与 Edge & Platform 的跨上下文契约。
- 本 Spec 完成后解除 `sign-workflow` 与 `case-push-workflow` 的 HTTP、事件、问题件定位和外部交互契约阻塞。

## 验收标准

- 每项待确认契约都有调用方、提供方、版本、字段、幂等键、错误处理与兼容策略，并经过用户确认。
- 固定值和长期规则已写入 `baseline.md` 或相应架构基准；未确认项明确保留为阻塞项，不以默认值代替。
- Sign 与 Push Feature 仅引用已登记的契约，不再各自定义相同字段或消息路由。
