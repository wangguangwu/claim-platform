# 平台契约版本化需求

## 项目背景与目标

签收与案件推送需要稳定的 HTTP、消息和外部系统边界，但其中一部分由平台自行决定，另一部分必须等待外部系统或具体租户确认。将两者放在同一“全部确认后才开始”的闸门中，会让 AI 无法推进平台自有工作，或诱导其伪造外部报文与租户协议。本 Spec 按决策权分档，先交付可由平台确定的契约草案与长期文档回写，再明确保留外部阻塞。

## 目标与非目标

### 目标

- A 档（平台自决）：起草并经用户确认签收 HTTP 子资源字段、MQ Topic/Tag/消费者组命名、问题件的对外定位字段命名与回复绑定语义、`SignErrorCode` 映射、MQ 重试与消费失败口径；确认后回写长期文档并解除对应实现阻塞。
- B 档（外部依赖）：登记审核、承保、内部案件、保司和**各真实租户**的真实报文、责任人、版本、幂等键、超时和错误语义；未确认时精确标记被阻塞的 Adapter、Consumer、租户接入项或契约测试。
- 保持新增字段追加兼容、破坏性变更新版本的规则，并使 Sign 与 Push Feature 只引用已登记的契约。

### 非目标

- 不实现 Controller、DTO、消息收发、外部客户端、Adapter 或契约测试代码。
- 不把 B 档外部报文、责任人或业务语义编造为默认值。
- 不修改基线已固定的路径、事件名称、错误码上报值和公共事件字段，除非用户明确确认。

## 所属上下文与范围

- 所属上下文：Sign、Push 与 Edge & Platform 的跨上下文契约。
- A 档确认后，解除 `sign-adaptation-collaboration` 中与 HTTP、消息路由、问题件对外定位命名和失败口径对应的实施闸门；`sign-core` 不依赖 A/B 档即可实施。
- B 档只解除所对应的承保、审核、案件、保司或某个租户的接入协同，不扩大到无关实现项；租户协议未确认不影响平台适配抽象与 `local` 测试租户 Pipeline 的实现。

## 验收标准

- A 档每一项均有草案、用户确认记录、版本、字段或命名、幂等/失败语义、兼容策略和明确的长期归属；确认后已回写 `baseline.md` 或相应架构基准。
- B 档每一项均有提供方、调用方、外部责任人、待确认内容与被阻塞实现项；没有未确认项被默认为可编码。
- Sign 与 Push Feature 的任务仅引用已经确认的契约；未确认项在任务中保持未完成并可追溯到本 Spec。
