## 背景

项目现有结构以 `backend/frontend` 为目录、以 `Claim Intake` 与 `Case Delivery` 为限界上下文命名，签收领域事实以"受理"作为统一词汇，租户协议适配与业务规则混在同一服务的接入层内。这与已定稿的目标架构不一致：目标架构要求前段叫签收、后段叫案件推送，租户差异只在边缘层表达，并要求后端只有网关、签收、案件推送三个可执行服务。

词汇与归属不一致带来三类成本：同一业务概念在不同文档、代码和数据库之间有三种叫法，跨人协作需要额外解释；目标架构中的推送与回执能力因为模块名不匹配而无从落位；后续按目标架构补齐能力时，每新增一个类都要重新判断它属于哪个服务。

本次是分阶段处理的第一阶段，只做结构、命名与分层归属的对齐，不新增业务能力。

## 目标

- 目录与模块按目标架构命名：前端工程、后端聚合工程、网关、签收服务、案件推送服务。
- 后端可执行服务只有三个：网关、签收服务、案件推送服务；共享技术模块继续存在但不承载业务领域事实。
- 理赔签收上下文的统一词汇从"受理"切换为"签收"，覆盖领域模型、用例输入输出、接入契约与测试命名。
- 用例分层形态统一：写入用例按命令与命令处理器组织，读取用例按查询服务组织。
- 租户协议差异的抽象命名与目标架构一致，为其后续迁入边缘层留出无需再改名的边界。
- 基线中的工程边界、限界上下文归属与分层包结构同步更新，使代码与规范单一来源。

## 非目标

- 不新增或改变任何业务能力：问题件、材料补充、案件撤销、案件推送任务、推送记录、保司回执本轮都不实现。
- 不把租户协议适配、认证、验签、加解密迁入网关；该迁移因网关使用响应式技术栈而需要独立方案，另立 Spec。
- 不改变数据库边界：库名、表名、列名、索引与既有迁移脚本全部保持不变。
- 不改变任何对外 HTTP 契约的路径、字段名、错误码语义与响应信封。
- 不新建前端功能域目录，前端本轮只调整工程目录与包名。
- 不修改 `docs/specs/archive/` 下的历史 Spec 内容。

## 需求与业务规则

1. 一个业务概念只允许一个词汇。理赔申请签收在其所属上下文中统一称为签收，其标识统一称为签收号，不再与"受理"混用。
2. 结构对齐不得改变业务行为。签收的三级幂等、发号与降级、并发锁、事务原子性、租户隔离与状态流转在本轮之后必须与之前完全一致。
3. 对外契约保持稳定。已实现的接入路径、请求字段、响应字段与错误码不因内部改名而变化；租户调用方无需感知本次调整。
4. 领域事实的归属边界不变。签收服务继续拥有签收、材料与交互日志事实；案件推送服务继续独立拥有案件、推送任务与回执事实；两者不得跨库读写。
5. 共享技术模块只承载无领域含义的技术能力与稳定契约，不得因为改名而接收任何业务实体或领域规则。
6. 网关本轮继续只承担路由与边缘职责，不承载签收或推送的业务规则，也不因目标结构图而新增空的职责目录。
7. 数据库与代码词汇允许暂时不一致。表名与列名保留既有命名，其与领域模型名的差异必须作为已知偏差在本 Spec 记录，供后续能力轮统一处理。
8. 与基线冲突时以更新后的 `docs/specs/baseline.md` 为准；本次涉及的基线变更已经用户确认。

## 所属限界上下文与范围

| 限界上下文 | 本次调整对象 | 是否改变领域事实 |
| --- | --- | --- |
| Edge & Platform（网关） | 无代码变更，仅在基线登记目标职责 | 否 |
| 理赔签收 | 目录、模块、包、领域词汇、用例分层归属、租户协议抽象命名 | 否 |
| 案件推送 | 目录、模块、包与启动类命名 | 否 |

范围之外：问题件与撤销的领域建模、材料与签收的状态扩展、推送任务与回执聚合、保司推送适配器、网关的认证与密码学能力、前端的六个功能域页面。

## 验收标准

- 目录与模块结构与目标架构一致，`mvn verify` 全部通过且测试数量与本轮开始前一致。
- 生产代码与测试中的类型、字段、方法与注释不再出现表示"受理"的领域词汇；对外契约与运行期契约的字符串取值（HTTP 路径、领域错误码、指标名、Redis 键前缀、库名与表列名）按 `design.md` 的取舍保持不变。
- 基线与 README 的项目结构、构建与启动路径与实际目录逐行一致，无失效引用。
- 写入用例全部表现为命令与命令处理器成对组织，读取用例全部表现为查询服务，不再存在同时承担两类职责的应用服务。
- 对外 HTTP 契约的路径、请求与响应字段、错误码在本轮前后完全一致，可由现有控制器与契约测试复核。
- 本轮不产生任何新增业务行为，问题件、撤销、推送与前端功能域保持未实现状态。
