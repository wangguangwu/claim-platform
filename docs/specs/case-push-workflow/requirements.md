# 案件推送流程需求

## 项目背景与目标

内部案件系统生成案件后，需要由平台向不同保司受控推送，并处理回执、失败重试和状态同步。签收服务只维护 `Sign → ClaimCase` 关系，不能承担案件推送事实；推送能力必须由独立的 Push 限界上下文拥有。

## 目标与非目标

- 接收版本化案件生成事件，为一个 `ClaimCase` 创建一个或多个可追踪的推送任务。
- 通过 `InsurerPushAdapter` 隔离保司协议差异，按租户、目标系统和适配器控制并发与配额。
- 记录推送尝试、处理保司回执、支持失败后的受控重试和状态同步。
- 对重复、乱序事件和重复回执保持幂等，不产生重复保司业务副作用。
- 不创建或修改 `ClaimCase` 业务事实，不审核、理算、核赔或支付；不写签收数据库，不直接引用 Sign 领域实体或跨库查询。

## 所属上下文与范围

- 所属限界上下文：Push；实现模块为 `claim-case-push-service`，独立拥有推送任务、推送记录、推送回执与推送策略。
- 本 Feature 依赖案件生成事件及保司交互契约完成确认；编码前必须建立并经确认 `docs/architecture/claim-case-push-service.md` 作为推送域内长期架构基准。

## 验收标准

- 同一案件生成事件重复投递只产生一次符合幂等规则的推送意图；同一案件可按策略产生多个推送任务。
- 每次推送尝试与回执均可按租户、案件、推送任务和 `traceId` 定位，不记录敏感报文原文。
- 重试只对允许重试的失败执行，达到策略阈值后转为可观测的失败状态，不无限重试。
- 回执和状态同步在重复、乱序或局部依赖失败时保持事实一致，且不影响签收服务数据。
