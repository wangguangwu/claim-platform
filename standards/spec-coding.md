# Spec Coding 规范

## 目录与文档

每项新增功能、跨限界上下文改动、共享契约变更或关键缺陷修复，均在 `specs/<feature-name>/` 建立小写 kebab-case 目录，并维护以下文件：

| 文件 | 必含内容 |
| --- | --- |
| `requirements.md` 或 `change.md` | 范围、非范围、所属限界上下文、EARS 验收需求、失败行为、幂等与兼容性影响 |
| `design.md` | 聚合、状态、接口或事件、数据归属、反腐层、失败补偿、并发与测试策略 |
| `tasks.md` | 可执行任务、依赖关系、需求回链、完成状态和证据 |

## 编写、Review 与实现顺序

1. 建立功能目录并确认范围、非范围和限界上下文。
2. 用 EARS 编写可验收需求，格式为 `WHEN [条件] THEN THE SYSTEM SHALL [行为]`。
3. 编写设计，明确命令幂等、异常边界、租户影响、兼容性和数据所有权。
4. 将设计拆为可执行任务；跨上下文任务需标明先后依赖。
5. 对 Spec 执行完整 Review，通过后才开始生产代码实现。
6. 按 `tasks.md` 的依赖顺序实施；每完成一个 Task，回写状态和对应验证证据。
7. 完成生产代码、迁移和测试后，回写迁移说明、已知限制和最终测试证据。

## Spec Review

Spec 完成或发生实质变化后，必须执行以下闭环检查：

| 检查方向 | 必须确认 |
| --- | --- |
| `FR → DS` | 每项需求都有设计承接；设计不引入无需求依据的功能；失败行为、幂等、租户和兼容性影响明确 |
| `DS → TK` | 每项设计都有可执行任务；任务覆盖迁移、配置、异常处理和必要测试；任务顺序满足依赖关系 |
| `TK → FR` | 完成所有任务可以满足每项需求及其验收标准 |

Review 不通过时，回到相应文档修正；不得用未记录的代码决策绕过 Review。

开发中发现变更时，按以下顺序同步：

- 需求或业务规则变化：先更新 `requirements.md`，再更新设计、任务并重新 Review；
- 设计变化：先更新 `design.md`，受影响时同步更新 `tasks.md`；
- 只改变实施进度或验证证据：更新 `tasks.md`，无需重写未受影响的需求和设计。

## Task 执行要求

- 每个 Task 必须标明关联的需求与设计编号、前置依赖、完成标准和验证证据位置。
- 实施时以当前 Task 和关联设计为主线；不得借机实现未列入范围的功能。
- 相关编译、测试或校验未通过时，Task 不得标记为完成；无法执行时记录原因、影响范围和风险。
- Task 完成并通过适用校验后，必须在开始下一 Task 前提交当前 Task 的全部相关修改；不得将多个 Task 混入同一 Commit。
- Task 完成状态必须与实际代码、迁移和测试证据一致。

## 追踪与完成门禁

- 使用 `FR-xxx → DS-xxx → TK-xxx → TEST-xxx` 追踪需求、设计、任务和测试证据。
- 聚合状态、幂等、消息消费、回执或并发领取必须有边界测试或属性测试。
- 服务 API、领域事件和外部适配器必须有契约测试及向后兼容性验证。
- 需求、设计、任务或测试证据不完整时，功能只能标记为 Draft 或 In Progress，不得标记为 Done。
